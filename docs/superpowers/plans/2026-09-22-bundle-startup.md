# Bundle and startup implementation plan

**Goal:** Reduce the JavaScript needed to open the empty workspace, with measured before/after evidence and unchanged import, preview, recovery and export behavior.

**Basis:** The user approved proceeding with the recommended Bundle & startup milestone after PR #16 was merged and deployed. The current product design and `plan/2026-09-19-product-roadmap-checklist.md` remain authoritative. This is a bounded change to existing loading boundaries, not a new engine or a browser-support expansion.

**Ownership:** Root owns this plan, requirements, acceptance and PR integration. The existing Sol high implementer owns product code, focused tests, the repeatable measurement harness and README/roadmap evidence in the isolated worktree. No concurrent product writers or worker delegation.

## Design and constraints

- Keep the `PdfEngine` interface and workspace interaction model unchanged. Prefer loading PDF.js inside the existing async PDF operations; do not add a general loader framework or delay the whole application behind a new loading screen.
- Empty startup must not fetch/evaluate PDF.js, its worker, the export worker/pdf-lib, or QPDF/pdfstudio assets. Image-only import and plain image export must not require PDF.js. PDF import/restore/preview loads the renderer on demand; output assembly remains in the export worker. Protected input/output alone should load security assets.
- Preserve eager recovery-record detection and the existing pending-work lock. Its code is small, and delaying it introduces a race before import; document this decision instead of forcing a recovery split for a checklist.
- Keep all document processing local, same-origin static assets only, copied PDF.js buffers, source bytes intact, additive rotation, strict missing/invalid-page export failure, original encrypted recovery bytes, and no stored passwords. Do not change cryptography, persistence schema, security headers, dependencies, deployment configuration or warning thresholds.
- Dynamic-load failure must leave a visible, understandable error and a usable workspace. A transient first-load failure must be retryable where the browser supports retry; do not leave a rejected application cache permanently poisoning the loader. Record any unavoidable browser module-cache limitation instead of inventing a cache-busting service.
- Account for cancellation while the renderer module is loading: a cancelled preview must not start a new render/task afterward or publish a stale result. Concurrent imports/renders must share the native module load and use a correctly configured same-origin worker.
- No user-facing speed guarantee. Report observed medians and tradeoffs, including any cost moved from startup to first PDF use.

## Review focus

- Hidden eager paths or automatic preloads that negate the split, especially recovery and image-only use.
- Module-load races, failed-promise caching, worker URL initialization and cancellation while awaiting imports.
- Original/source/unlocked buffers, passwords and recovery locks across first use and failed runtime loads.
- Honest cache/transfer/decoded-size accounting, matched samples and no privacy-route interference with warm-cache measurements.
- Usability during first-use loading, actionable errors, preview retry and no lost selection/workspace.
